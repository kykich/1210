## 1. Цель и назначение

Развернуть на VPS (Ubuntu 25.10, белый IP) **публичный веб-чат с локальной
LLM**, работающей на этом же сервере. Сервис предназначен для **тестирования
работы LLM по сети**: любой, кто знает IP-адрес, открывает страницу чата и
общается с локальной моделью.

Инференс — полностью локальный (модель `.gguf` на диске VPS, движок
`llama.cpp`). Внешние облачные API (DeepSeek/GigaChat) в этом режиме НЕ
используются.

### 1.1. Целевой результат (критерии приёмки)

1. **Доступ по сети** — сервис отвечает по белому IP VPS (порт по умолчанию
   **80**, конфигурируемый), страница чата открывается из внешней сети.
2. **Не более 2 активных сессий** — одновременно работают максимум **2
   пользовательские сессии**; 3-й подключившийся получает **заглушку «нет
   свободной сессии»**. Сервис не падает, работающие сессии не страдают
   (см. §5).
3. **Базовые ограничения** — настроены лимит активных сессий, rate limit и
   ограничение контекста (`max context`) + `max_tokens`.
4. **Приватность инференса** — текст запросов не уходит на внешние API;
   наружу доступен только публичный веб-порт, порт движка закрыт.

## 2. Решения по уточнённым требованиям заказчика

| № | Требование | Решение |
|---|---|---|
| 1 | Русский язык, слабая модель достаточна | Модель 3B-класса, `Q4_K_M` (см. §4) |
| 2 | Домена нет, только IP | Сервис на `http://<IP>:<PORT>`; порт по умолчанию **80**, конфигурируемый. TLS не требуется |
| 3 | Публичный чат «для тех, кто знает IP» | **Без аутентификации.** Защита — лимит активных сессий + rate limit |
| 4 | Не более 2 одновременно, остальные — заглушка | **Лимит 2 АКТИВНЫХ сессии.** 3-й и далее получают страницу-заглушку «нет свободной сессии» (см. §5) |
| 5 | Память/профили/история — по выбору пользователя | Функционал UI сохраняется; **у каждого пользователя СВОЯ изолированная сессия** (см. §6) |

Ключевые архитектурные уточнения:

- **Прокси — `nginx`.** Публичный порт (по умолчанию 80) обслуживает `nginx`,
  который проксирует запросы на app-сервис `127.0.0.1:8000` (см. §8.1).
- **Сессии — на клиента.** Все пользователи больше НЕ сидят в одной общей
  сессии: каждому браузеру — своя независимая сессия (диалог, память,
  профили). Cookie-идентификатор → свой `SessionStore` (см. §5.2, §6.2).
- **Лимит активных сессий = 2.** При подключении 3-й сессии пользователю
  отдаётся **заглушка** «нет свободной сессии» (см. §5.1).
- **Контрольный пинг при отвлечении (запрос-ответ).** Сервер решает и
  помечает сессию «на проверке» после тишины; браузер тихо опрашивает
  `/api/heartbeat` и показывает диалог «Вы здесь?». Через nginx —
  обычный проксинг. Подробно — §5.4.
- **RAG/MCP — в дальнейшем.** На текущем этапе реализуется только чат
  (см. §6).

> **Следствие из п.3+п.4:** сервис общедоступный → основной механизм защиты
> это ограничение числа **активных сессий** (2) и частоты запросов.

## 3. Ресурсы VPS и ограничения (зафиксировано)

- CPU: **2 vCPU**
- RAM: **4 ГБ**
- Диск: **60 ГБ**
- GPU: **отсутствует** → инференс только на CPU
- ОС: Ubuntu 25.10, GNU/Linux 6.17.0-41-generic, x86_64

### 3.1. Бюджет памяти (пример: 3B Q4_K_M, ctx 4096)

| Потребитель | ~RAM |
|---|---|
| ОС + systemd + ssh + nginx | 500–800 МБ |
| `llama-server` (модель 3B Q4_K_M) | ~2.0 ГБ |
| KV-кэш (ctx 4096) | ~200–400 МБ |
| app-сервис (Python) | ~100–200 МБ |
| **Итого** | **~2.9–3.4 ГБ** (влезает в 4 ГБ с запасом) |

> Модель 7B/8B (`~4.4–5 ГБ`) в 4 ГБ **НЕ влезает** → не рассматривается.
> Контекст надо держать небольшим (2048–4096), иначе KV-кэш съест запас.

### 3.2. Ожидаемая производительность

- Скорость генерации на 2 vCPU для 3B Q4: **~3–8 токенов/с**.
- Ответ ~300 токенов → **~40–90 с**. Это **медленно**.
- Следствия: **обязателен стриминг (SSE)** (§8), увеличенные таймауты (§5),
  скромный `max_tokens` (§7).

## 4. Модель и движок инференса

### 4.1. Модель

- Класс: **3B, инструктивная**, с хорошим русским.
- Кандидаты (выбрать по результатам замера):
  - `Qwen2.5-3B-Instruct` (Q4_K_M) — хороший русский;
  - `Llama-3.2-3B-Instruct` (Q4_K_M).
- Квант: `Q4_K_M` (баланс качество/размер). При нехватке памяти — `Q4_K_S`.

### 4.2. Движок llama.cpp (CPU-only)

- Сборка под x86_64 (AVX2), без CUDA.
- Вариант установки: prebuilt-бинарники `llama-server` для Linux (релиз
  ggml-org/llama.cpp) либо сборка из исходников.

### 4.3. Параметры запуска `llama-server`

| Параметр | Значение | Обоснование |
|---|---|---|
| `-m <model.gguf>` | путь к модели | — |
| `--alias <name>` | напр. `local-3b` | имя модели в API |
| `--host 127.0.0.1` | loopback | движок НЕ публикуем наружу |
| `--port 8080` | — | локальный порт |
| `-c <ctx>` | `4096` | баланс RAM / KV-кэш |
| `-ngl 0` | без GPU | нет видеокарты |
| `-t 2` | 2 | по числу vCPU (не более) |
| `-fa auto` | flash-attn | ускорение на CPU |
| `--jinja` | включить | шаблон чата модели |
| `--api-key <KEY>` | задать | защита движка (доп. слой) |
| `--parallel 1` | 1 слот | см. §5 (сериализация инференса) |

> **Важно про `--parallel` и `-c`:** в llama.cpp общий `-c` делится между
> слотами. При `--parallel 2` каждому слоту достанется половина контекста, а
> 2 vCPU будут драться за CPU. Поэтому по умолчанию `--parallel 1`: до 2
> активных клиентских сессий допускаются, но фактические инференсы
> сериализуются движком. Вариант `--parallel 2` — опция, если приёмка
> потребует истинной параллели (с уменьшением `-c` до 2048 и замедлением).

## 5. Лимит сессий, жизненный цикл и контрольный пинг (ядро ТЗ)

Требование: **не более 2 активных сессий**; 3-й подключившийся получает
заглушку. При отвлечении пользователя — **контрольный пинг**, при отсутствии
ответа в течение минуты — **сессия отключается** (слот освобождается),
в окне остаётся только просмотр истории.

### 5.1. Жизненный цикл сессии (конечный автомат)

```
            запрос/ответ
   ┌─────────────────────────────┐
   │                             ▼
[ACTIVE] --60 с без активности--> [CHECK] --30 с без ответа--> [OFFLINE]
   ▲                                 │                              │
   └────── ответ пользователя ───────┘                              ▼
                                                       (слот освобождён; страница
                                                        переходит в read-only:
                                                        история видна, ввод заблокирован)
```

Состояния сессии:

| Состояние | Слот занят | Что видит пользователь | Новые запросы |
|---|---|---|---|
| `ACTIVE` | да | обычный чат | разрешены |
| `CHECK` | да | диалог «Вы здесь? Продолжить?» + **обратный отсчёт 1 мин** | разрешены (ответ продлевает) |
| `OFFLINE` | **нет** (освобождён) | **только просмотр истории**, поле ввода заблокировано | запрещены |

Правила:

- **Активность** = реальный запрос к `/api/*` **или** ответ пользователя в
  диалоге «Продолжить?». Тихое опрашивание `/api/heartbeat` **само по себе
  активностью НЕ является** и сессию не продлевает.
- **`IDLE_TIMEOUT` (по умолчанию 60 с) без активности** → сессия переходит в
  `CHECK` (сервер лишь помечает; сообщение пользователю доставляет клиент,
  см. §5.4).
- **`CHECK_TIMEOUT` (по умолчанию 30 с) без ответа** в `CHECK` → сессия
  переходит в `OFFLINE`, слот освобождается. История при этом остаётся
  видимой в уже открытом окне (страница держит её у себя, см. §5.5).
- Cookie-идентификатор `sid` **не привязан к IP** — смена IP не создаёт
  новую сессию (по решению заказчика). Сессия опознаётся только по cookie.

### 5.2. Изоляция и реестр сессий

Переход с одной глобальной сессии на **сессии на клиента**:

1. **Реестр:** `_ServerState.session` → словарь `sessions: {sid:
   SessionStore}` под общим `Lock`; запись состояния (`ACTIVE/CHECK/OFFLINE`)
   и `last_seen` рядом.
2. **Изоляция данных:** каждая сессия пишет в СВОЙ файл
   `session/<sid>.json` (в `SessionStore` уже есть параметр `path=`).
3. **cookie `sid`:** выдаётся сервером (`Set-Cookie`), читается из запроса;
   значение — случайное (`secrets.token_urlsafe`), флаг `HttpOnly`.
4. **Агент — общий и потокобезопасный** (не хранит изменяемого состояния
   запроса; проверить/обернуть).
5. **Внутрисессионные гонки** (сжатие, авто-переход задачи) — под `RLock` в
   `SessionStore`; проверить `_maybe_auto_compact` / `_maybe_advance_task`.
6. **Сборщик мусора сессий:** периодически освобождает `OFFLINE`-сессии и
   чистит «мёртвые» (см. §5.3), чтобы слоты не «залипали».

### 5.3. Управление слотами

- **Лимит активных сессий = 2** (конфигурируемо, `RTK_MAX_SESSIONS`).
- **Заглушка** при подключении 3-й сессии: HTML-страница «нет свободной
  сессии» (HTTP `503`) + мета-обновление (`Refresh: 15`) или кнопка
  «повторить». Без раскрытия деталей.
- Слот освобождается при переходе сессии в `OFFLINE` (по таймауту §5.1) или
  при явном выходе.
- **Фоновая очистка:** поток-сборщик раз в ~30 с:
  - `ACTIVE` без активности ≥ `IDLE_TIMEOUT` → в `CHECK`;
  - `CHECK` без ответа ≥ `CHECK_TIMEOUT` → в `OFFLINE`, освобождение слота;
  - `OFFLINE` старше суток → удаление реестровой записи (файл сессии можно
    сохранять для истории).

> **Таймауты сделаны КОРОТКИМИ (`IDLE_TIMEOUT=60`, `CHECK_TIMEOUT=30`).**
> Причина: закрытая вкладка НИЧЕГО не сообщает серверу, поэтому слот реально
> освобождается лишь через `IDLE_TIMEOUT + CHECK_TIMEOUT`. При прежних
> 300/60 слот «висел» ~6 минут, и при нескольких вкладках/перезагрузках
> страницы владелец стабильно видел «нет свободной сессии».

#### 5.3.1. Приоритетный слот владельца (`RTK_OWNER_TOKEN`)

Проблема: HTTP-сервер **не может** понять по SSH-туннелю, что запрос «свой»
(туннель — транспорт до модели, в браузерной сессии следа не оставляет),
а сессии освобождаются только по таймауту. Поэтому приоритет даётся по
**секретному токену владельца**:

- Оператор задаёт секрет в ENV: `RTK_OWNER_TOKEN=<секрет>`
  (напр. в `/etc/rtk/rtk-web.env`; **НЕ** в коде — проект публичный).
- Владелец открывает ссылку `http://<IP>/?owner=<секрет>`. Сервер сверяет
  токен, выдаёт cookie `owner` и **редиректом очищает адресную строку**
  (чтобы секрет не оставался в истории/Referer).
- При нехватке слотов привилегированному запросу **всегда** находится место:
  самая старая **непривилегированная** сессия вытесняется в `OFFLINE`.
- Владельческие сессии **не вытесняют друг друга**; обычные пользователи
  работают с прежним лимитом.
- Токен можно также прислать в cookie `owner` или заголовке `X-Owner-Token`
  (для скриптов/`curl`). Пустой `RTK_OWNER_TOKEN` — приоритет выключен.
- Тест: `tests/check_owner_priority.py`.

### 5.4. Контрольный пинг (запрос-ответ)

Канал — **запрос-ответ**, решение принимает **сервер**:

- Сервер по таймеру (фоновая очистка §5.3) переводит «замолчавшую» сессию из
  `ACTIVE` в `CHECK`.
- Клиент **тихо опрашивает** `GET /api/heartbeat` (лёгкий таймер, раз в
  ~30 с). Ответ содержит состояние сессии:
  `{state: "active"|"check"|"offline", deadline: <ISO, до конца CHECK>}`.
- При `state == "check"` клиент показывает диалог **«Вы здесь? Продолжить?»**
  с **обратным отсчётом до `deadline`** (по умолчанию 30 с).
  - Пользователь нажал «Продолжить» (или отправил сообщение) → запрос к
    `/api/*` обновляет `last_seen`, сессия возвращается в `ACTIVE`.
  - Ответа нет до `deadline` → сессия в `OFFLINE`.
- При `state == "offline"` клиент переводит страницу в **read-only**
  (см. §5.5) и предлагает «Начать новую сессию» (если слот свободен; иначе —
  заглушка).

> `/api/heartbeat` **не продлевает** сессию и **не считается активностью** —
> он лишь доставляет решение сервера пользователю.

### 5.5. Просмотр истории после отключения (read-only)

- История диалога остаётся видимой **пока открыто окно браузера**: страница
  держит её в JS-памяти (последние снимки из `/api/session`), после
  отключения с сервера ничего не подгружается.
- Поле ввода и кнопка отправки **блокируются**; показывается плашка «Сессия
  завершена. История доступна для просмотра».
- Кнопка «Начать новую сессию» повторно запрашивает слот (при отсутствии
  свободного слота — заглушка §5.3).
- (Опционально) сервер может отдавать сохранённую историю `OFFLINE`-сессии по
  прямому запросу `GET /api/session` — но **без права писать** (только чтение).

### 5.6. Таймауты

- `LOCAL_TIMEOUT` — поднять до ~300 с (медленная генерация).
- HTTP-таймаут app-сервера — согласовать с таймаутом генерации.
- `llama-server` — таймаут не задаётся (движок считает столько, сколько надо).

## 6. Состав приложения

По п.5 требований — **весь существующий функционал интерфейса сохраняется**,
никакого урезания. Пользователь сам выбирает, что использовать:

- Чат (вопрос → ответ локальной модели);
- Параметры генерации (temperature/top_p/repetition_penalty/max_tokens/ctx);
- История диалога, сжатие summary, стратегии контекста (none/sliding/facts/branch);
- Память агента (working/longterm), профили (персоны);
- Инварианты, состояние задачи.

### 6.1. Этапность

- **Текущий этап — только чат.** На приёмку выходят: доступ по сети, лимит
  активных сессий, жизненный цикл сессии с контрольным пингом, ограничения
  контекста/токенов, rate limit, приватность.
- **RAG/MCP — в дальнейшем.** Модули остаются в коде; их наличие на VPS
  (Ollama для эмбеддингов, MCP-серверы) **не гарантируется** на этом этапе.
  Требование: код должен корректно деградировать (статус «недоступно»), не
  роняя чат.

### 6.2. Изменения в коде

| Файл | Что меняем |
|---|---|
| `rtk_app/config.py` | `WEB_HOST`/порт из ENV (`RTK_HOST=127.0.0.1` за nginx, `RTK_PORT`); `RTK_MAX_SESSIONS=2`, `RTK_IDLE_TIMEOUT=60`, `RTK_CHECK_TIMEOUT=30`; `RTK_OWNER_TOKEN` (приоритет владельца); параметры llama из ENV |
| `web/server.py` | реестр сессий `sid -> SessionStore` + состояние `ACTIVE/CHECK/OFFLINE`; cookie `sid`; cookie/URL-токен `owner`; заглушка при отсутствии слота; `/api/heartbeat`; `/api/health`; привязка к loopback; фоновая очистка |
| `web/session_manager.py` | привилегированные (владельческие) сессии: `privileged`-флаг, вытеснение самой старой обычной сессии при нехватке слотов |
| `web/static/js` (UI) | таймер опроса `/api/heartbeat`; диалог «Продолжить?» с отсчётом; перевод в read-only и блокировка ввода |
| `web/templates` (или inline) | **страница-заглушка** «нет свободной сессии» |
| `rtk_app/session_store.py` | сессии с явным путём `session/<sid>.json` (уже поддерживается через `path=`) |
| `rtk_app/local_server.py` | хост движка `127.0.0.1`; `--parallel`, `--api-key`, `-c` в конфиг |
| `rtk_web.py` | ключи облачных моделей не требовать в серверном режиме (не валить самодиагностику) |
| `rtk_app/local_llm.py` | уже готов (OpenAI-совместимый API + Bearer); передавать `--api-key` |
| `deploy/nginx.conf` | reverse-proxy порт → 127.0.0.1:8000; `proxy_read_timeout`; `proxy_buffering off` (для SSE); `X-Forwarded-For` |
| `deploy/*.service` | systemd-юниты `llama-server` и `rtk-web` |

## 7. Базовые ограничения

### 7.1. Max context

- Движок: `-c 4096` (общий бюджет).
- App: обрезка истории по `config.CONTEXT_WINDOW_*` (уже есть). Валидация:
  ввод/история сверх лимита → не пропускать, вернуть понятную ошибку.
- Значение по умолчанию: **4096** токенов.

### 7.2. Max tokens (вывод)

- Поддержано (`agent._coerce_max_tokens`, `MAX_TOKENS_MAX`).
- Серверный дефолт: **512**; потолок: **1024** (при ~5 ток/с дольше = долго).

### 7.3. Длина входного сообщения

- Ограничить `question` (символы/токены): например **≤ 8000 символов**.
- Ограничить размер всего JSON-тела запроса (`Content-Length`).

### 7.4. Rate limit

| Уровень | Механизм | Значение (по умолчанию) |
|---|---|---|
| Приложение | лимит **активных сессий** | **2** (§5) |
| Приложение | token bucket по IP | **10 запросов/мин на IP** |
| Приложение | таймаут простоя (`ACTIVE`→`CHECK`) | **60 с** |
| Приложение | окно проверки (`CHECK`→`OFFLINE`) | **30 с** |

- Продлевает сессию только реальный запрос `/api/*` ( **не** `/api/heartbeat`).
- При превышении частоты — `429` + `Retry-After`.
- При превышении числа сессий/`OFFLINE` — заглушка `503` «нет свободной сессии».
- IP берётся из `X-Forwarded-For` (за nginx — обязательно прокидывать) или
  из сокета. **Cookie `sid` к IP НЕ привязан** (смена IP ≠ новая сессия).

## 8. HTTP-слой и транспорт

### 8.1. Публикация (nginx)

- `nginx` слушает публичный порт (по умолчанию **80**), проксирует на app
  `127.0.0.1:8000`.
- app-сервис слушает только loopback (`127.0.0.1:8000`) — наружу не торчит.
- `llama-server` — строго `127.0.0.1:8080`, наружу НЕ публикуется.
- nginx прокидывает `X-Forwarded-For` и `X-Real-IP` (для rate limit по IP).
- Контрольный пинг (§5.4) идёт обычным запросом через тот же proxy — без
  специальной настройки (SSE при этом не требуется; см. §8.3 для стриминга
  ответа `/api/ask`).

Порт (по умолчанию 80, конфигурируемо) задаётся в `deploy/nginx.conf` и в
ENV app-сервиса.

### 8.2. Эндпоинты (минимум)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/` | страница чата (или заглушка при отсутствии слота) |
| GET | `/css/*`, `/js/*` | статика |
| POST | `/api/ask` | вопрос → ответ (есть) |
| GET | `/api/heartbeat` | **новый**: состояние сессии (`active/check/offline`) + `deadline` |
| GET | `/api/health` | **новый**: живость app + llama-server (мониторинг) |
| GET/POST | `/api/*` | остальные (session, profiles, memory, …) — как есть |

- Все `/api/*` (кроме `/api/health`) привязаны к сессии по cookie `sid`.
- При отсутствии свободного слота `/api/*` возвращают `503`; для `GET /` —
  HTML-заглушка.
- `/api/heartbeat` **не продлевает** сессию.

### 8.3. Стриминг (обязателен)

- Сейчас `stream:false` → браузер «висит» 40–90 с.
- Ввести **SSE** (`stream:true`) хотя бы для `/api/ask`: токены отдаются по
  мере генерации. `llama.cpp` поддерживает OpenAI-совместимый стриминг.
- При nginx: `proxy_buffering off`, `proxy_read_timeout 300s+`,
  `X-Accel-Buffering: no`.

### 8.4. Ошибки

Единый JSON: `{ok:false, error, ...}`.
Коды: `400` (неверный запрос/лимит контекста), `429` (rate limit),
`503` (нет свободной сессии/сессия offline), `504` (таймаут upstream).

## 9. Безопасность и приватность

- **Аутентификация отсутствует** (публичный чат по IP, требование п.3).
- Понимание риска: любой с IP может занимать сессию → компенсируем лимитом
  активных сессий (§5) и rate limit (§7.4).
- `llama-server --api-key` + loopback-привязка (движок не торчит наружу).
- Фаервол `ufw`: открыть **только 22 и публичный порт (80)**; 8000/8080 закрыть.
- `Cache-Control: no-store` (уже), жёсткий `Content-Type`, ограничение размера
  тела и заголовков.
- **Логи без тел запросов** (приватность): только метаданные (время, IP,
  размер, код ответа).
- Отсутствие секретов в публичном коде; `--api-key` хранить в файле с правами
  `600`, вне git.

## 11. Тестирование и приёмка (чек-лист)

1. **Доступ по сети**: с внешней машины `http://<IP>/` открывает чат;
   `curl http://<IP>/api/ask` отвечает.
2. **Лимит сессий**: две сессии работают независимо; третья получает
   заглушку «нет свободной сессии»; работающие сессии не страдают.
3. **Изоляция сессий**: диалог/память/профили одной сессии не видны в другой.
4. **Жизненный цикл**: после 5 мин тишины сессия → `CHECK` (пользователь
   видит «Вы здесь?»); ответ продлевает; без ответа через 1 мин → `OFFLINE`,
   слот освобождается.
5. **Read-only после отключения**: история видна, ввод заблокирован; новая
   сессия берёт слот (или заглушка, если мест нет).
6. **Rate limit**: превышение частоты → `429` + `Retry-After`.
7. **Max context**: слишком длинный ввод/история → понятная ошибка, без OOM.
8. **Max tokens**: ответ не длиннее лимита.
9. **Стриминг**: токены приходят постепенно (SSE), не «залпом в конце».
10. **Приватность**: порты llama (`8080`) и app (`8000`) недоступны извне;
    логи без тел.
11. **Рестарт**: `systemctl restart` поднимает сервис; автозапуск после
    перезагрузки.
12. **Память**: под нагрузкой RAM не превышает 4 ГБ (мониторить `free -h`).

## 12. Риски и открытые вопросы

### Риски

- **Медленный CPU-инференс** (главный риск): UX страдает без стриминга;
  большие ответы долго. Митигация: SSE + `max_tokens` 512.
- **«Мёртвые» сессии**: могут занять оба слота. Митигация: автомат состояний
  (§5.1) + фоновая очистка (§5.3).
- **Потеря контекста при `OFFLINE`**: сервер не продлевает; пользователь
  может открыть новую сессию — история видна в старом окне. (Опционально:
  чтение сохранённой истории, §5.5.)
- **OOM при параллели**: KV-кэш и очередь могут выйти за 4 ГБ. Митигация:
  ctx 4096, `--parallel 1`, swap, мониторинг.
- **Модель 3B слабая** — качество ответов ограничено (приемлемо по п.1).
