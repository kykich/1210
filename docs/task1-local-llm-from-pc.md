## 1. Цель и назначение

Дать оператору возможность **подключить мощную LLM, установленную на его
личном ПК, к чат-сервису на VPS** — без публикации ПК в интернет и без
облачных API. Связь ПК и VPS идёт через **SSH-туннель** (ПК инициирует
соединение к VPS, т.к. «локальный ПК по ssh подключён к vps»).

После подключения:
- в разделе UI **«Локальная модель»** появляется список LLM, найденных на ПК;
- по кнопке **«Запустить»** поднимается туннель и ПК получает **запрос на
  подтверждение** (пользователь на ПК разрешает подключение);
- по умолчанию в чате используется **слабая** модель VPS (`Qwen-2B`);
- после запуска **сильной** модели с ПК (`Qwen-9B`) её имя **заменяет** имя
  модели в интерфейсе — дальше чат отвечает сильной моделью.

### 1.1. Целевой результат (критерии приёмки)

1. **Регистрация ПК.** На VPS (в разделе «Локальная модель») можно указать
   путь к папке с моделями **на ПК**; после «индексирования» выводятся
   доступные LLM (`.gguf`) с ПК.
2. **Запуск и подтверждение.** Кнопка «Запустить» инициирует SSH-туннель
   ПК↔VPS; на ПК появляется **запрос на подтверждение**; без подтверждения
   туннель не считается активным.
3. **Переключение имени/модели.** Пока туннель не поднят — активна слабая
   `Qwen-2B` (VPS). После запуска `Qwen-9B` (ПК) имя активной модели в UI
   **меняется на сильную**, и чат отвечает ею.
4. **Изоляция и устойчивость.** Если ПК/туннель отвалился — сервис
   **деградирует на слабую** `Qwen-2B` (или отдаёт понятную ошибку), не падая.
5. **Безопасность.** ПК не публикуется в интернет; порт движка ПК не торчит
   наружу; доступ к туннелю — только по SSH-ключу; подтверждение на ПК.

## 2. Терминология и текущее состояние

| Термин | Значение |
|---|---|
| **ПК** | личная машина оператора с LLM (llama.cpp `llama-server`), обычно за NAT, с GPU |
| **VPS** | сервер с публичным IP, где работают `rtk-web` (чат) и слабый `llama-server` (`Qwen-2B`) |
| **Туннель** | SSH-соединение ПК→VPS, пробрасывающее порт движка ПК на VPS (reverse-форвардинг) |
| **Слабая** | `Qwen-2B` — модель на VPS (CPU), активна по умолчанию |
| **Сильная** | `Qwen-9B` — модель на ПК (GPU), активируется после запуска |

### 2.1. Что уже есть (факты из кода/деплоя)

- **VPS:** `llama-server.service` — слабая модель, `127.0.0.1:8080`,
  `--api-key <LLAMA_KEY>`, alias `local-3b` (переименовать в `Qwen-2B`).
- **UI:** сворачиваемая секция **«Локальная модель»** (`index.html`,
  `data-section="local"`), элементы: `local-enabled`, `local-root`,
  `local-server`, `local-model`, кнопки `local-scan` / `local-start` /
  `local-stop` / `local-status-btn` (`js/app.js`).
- **API:** `GET/POST /api/local` (`web/server.py`, `_handle_local`):
  `scan` (поиск сервера и `.gguf`), `params` (автоподбор `ngl` по VRAM),
  `start`/`stop`/`status`/`models`/`set`.
- **Движок:** `rtk_app/local_server.py` (скан, `suggest_params`, запуск
  подпроцесса, проверка `/v1/models` с `Authorization: Bearer`),
  `rtk_app/local_llm.py` (OpenAI-совместимый клиент).
- **Конфиг:** `config.LOCAL_*` (`RTK_LOCAL_HOST/PORT/API_KEY/LABEL/CTX/…`),
  `config.LOCAL_API_KEY` = `RTK_LOCAL_API_KEY` (совпадает с `LLAMA_KEY`).
- **Агент:** `Agent.set_local_model(url, model, label)` добавляет источник
  `local` в селектор моделей.

> **Ключевое наблюдение.** Сейчас блок «Локальная модель» умеет запускать
> `llama-server` **как подпроцесс на той же машине, где крутится `rtk-web`**
> (т.е. на VPS). Он **НЕ умеет**: (а) сканировать папку на другом ПК,
> (б) поднимать SSH-туннель, (в) запрашивать подтверждение на ПК. Это и есть
> предмет доработки.

### 2.2. Направление SSH-туннеля

«Локальный ПК по SSH подключён к VPS» → инициатор — **ПК**. Значит нужен
**reverse-туннель**: на ПК запускается

```
ssh -N -R 127.0.0.1:18080:127.0.0.1:8080 rtk@<VPS>
```

Тогда движок на ПК (`127.0.0.1:8080`) становится доступен **на VPS** как
`127.0.0.1:18080`, и `rtk-web` обращается к сильной модели по этому адресу.
(Прямой `-L` невозможен: VPS не может инициировать соединение к ПК за NAT.)

## 3. Архитектура (предлагаемая)

```
        ┌────────────────────────── VPS (белый IP) ──────────────────────────┐
        │  rtk-web (127.0.0.1:8000)  ──►  Agent ──► источники моделей          │
        │                                            │                         │
        │         ┌──────────────────────────────────┴───────────────┐        │
        │         ▼                                                  ▼        │
        │  llama-server (слабая)                         127.0.0.1:18080         │
        │  127.0.0.1:8080  Qwen-2B                       (reverse-туннель)       │
        │         ▲ (active по умолчанию)                         ▲            │
        └─────────┼───────────────────────────────────────────────┼────────────┘
                  │                                          SSH (-R)
                  │                                               │
                  │                                    ┌──────────┴───────────┐
                  │                                    │  ПК оператора (NAT)  │
                  │                                    │  llama-server Qwen-9B│
                  │                                    │  127.0.0.1:8080      │
                  │                                    │  + подтверждение     │
                  └────────────────────────────────────┴──────────────────────┘
```

Управление туннелем — **принято: ПК инициатор, постоянный туннель (вариант B)**:

- **ПК (Windows) держит ПОСТОЯННЫЙ reverse-туннель** к VPS (`ssh -N -R`),
  поддерживаемый окном-агентом на ПК и авто-перезапуском (см. §10.2).
- VPS по кнопке «Запустить» лишь **включает** уже поднятый туннель
  (переключает источник `local` на `127.0.0.1:18080`).
- **Подтверждение** на ПК — **один раз на SSH-сессию** (пока живо
  SSH-соединение ПК↔VPS): окно-агент спрашивает «Разрешить подключение
  VPS `<IP>`?», ответ запоминается до конца сессии SSH; при разрыве и
  переподключении — спрашивает заново.
- **При обрыве** туннеля/ПК — **авто-возврат на слабую `Qwen-2B`**; сильная
  подключается снова только после повторного подключения (авто-возврат
  двусторонний по факту восстановления туннеля).

> Варианты (A) «VPS поднимает туннель к ПК» и (C) «гибрид» **отклонены**:
> ПК за NAT, Windows, соединение исходящее ПК→VPS.

## 4. Функциональные требования

### 4.1. Указание пути и «индексирование» моделей с ПК

- В разделе «Локальная модель» поле **корня папки** должно позволять указать
  путь **на ПК** (например, `D:\models\llama` на Windows).
- Так как VPS напрямую папку ПК не видит, «индексирование» выполняется
  **на ПК** (окно-агент на ПК) и его результат возвращается на VPS:
  - ПК сканирует папку (рекурсивно) на `llama-server(.exe)` и `*.gguf`;
  - список моделей (имя, путь, размер, число слоёв) отправляется на VPS
    (через тот же SSH-канал, отдельным запросом или файлом-ответом);
  - VPS показывает список в UI (селект `local-model`).
- Минимальный объём данных: `[{name, path, size_mb, quant}]`.

### 4.2. Кнопка «Запустить» — поднятие туннеля

- По кнопке **«Запустить»** (`local-start`):
  1. VPS проверяет доступность туннеля к ПК (порт `127.0.0.1:18080`).
  2. Если туннель не поднят — отправляет на ПК-агент **запрос на запуск**.
  3. ПК поднимает (или поддерживает) reverse-туннель.
  4. VPS проверяет `/v1/models` (с `Bearer`) и включает источник `local`.

### 4.3. Запрос с подтверждением со стороны пользователя (на ПК)

- На ПК **обязательно** всплывает **окно-агент**: «VPS `<IP>` просит
  подключить локальную LLM. Разрешить?» — с кнопками **Разрешить / Отклонить**.
- **Подтверждение — один раз на SSH-сессию** (пока SSH-соединение ПК↔VPS
  живо). Ответ запоминается в окне-агенте до разрыва соединения; при
  переподключении (новое SSH-соединение) — запрос появляется **заново**.
- До подтверждения туннель **не** считается «активным» для VPS: VPS видит
  туннель, но не включает сильную модель, пока не пришло подтверждение.
- «Отклонить» → туннель закрывается/не активируется; остаётся слабая
  `Qwen-2B`.
- Таймаут ожидания подтверждения — 120 с (по умолч.); по истечении — отказ.

### 4.4. Переключение слабая ↔ сильная и имя модели

- По умолчанию активна **слабая** (`Qwen-2B`, VPS, `127.0.0.1:8080`).
- После запуска **сильной** (`Qwen-9B`, ПК, `127.0.0.1:18080`):
  - источник `local` агента переключается на URL туннеля и модель `Qwen-9B`;
  - **имя активной модели в UI меняется на сильную** — в интерфейсе
    **показывается имя АКТИВНОЙ модели** (в селекторе и в заголовке/карточке
    отображается только `Qwen-9B`, без списка обеих);
  - чат отвечает сильной моделью.
- Кнопка **«Остановить»**: закрывает туннель, возвращает **слабую**
  `Qwen-2B` как активную (имя в UI — снова слабая).

### 4.5. Деградация и авто-возврат при обрыве

- Обрыв туннеля/ПК → `rtk-web` **не падает**:
  - активный источник **автоматически возвращается** на слабую `Qwen-2B`;
  - в UI статус: «ПК недоступен, используется Qwen-2B» (имя активной модели —
    снова слабая).
- **Авто-возврат двусторонний:** когда туннель восстановлен (ПК снова
  подключился и подтвердил SSH-сессию), VPS **сам** переключается обратно на
  сильную `Qwen-9B` — отдельное нажатие кнопки не требуется.
- Проверка живости туннеля — периодический `GET /v1/models` по
  `127.0.0.1:18080` (см. §10.2).

---

## 5. Нефункциональные требования

- **Непубличность ПК.** ПК не слушает внешние порты; соединение только
  исходящее (ПК→VPS).
- **Только SSH-ключ.** Без паролей; ключ — отдельный, с ограничением
  (`command=`, `permitopen`/`permitlisten`, `no-pty`) где возможно.
- **Идемпотентность.** Повторный «Запустить» не плодит туннели.
- **Таймауты.** Подтверждение на ПК — с таймаутом (по умолч. 120 с); по
  истечении — отказ.
- **Логи без содержимого запросов** (приватность), только метаданные.
- **Конфиденциальность путей ПК** — не печатать в публичных логах VPS.

## 7. Поток взаимодействия (принятый сценарий)

1. **Подготовка (однократно):** на ПК (Windows) генерируется SSH-ключ
   (`ssh-keygen`), публичная часть кладётся на VPS
   (`~rtk/.ssh/authorized_keys`) с ограничениями (`no-pty`,
   `permitlisten="127.0.0.1:18080"`, при возможности `command=`).
2. На ПК запускается **окно-агент** (`rtk_pc_agent`, из «Автозагрузки»).
   Агент держит **постоянный reverse-туннель** `ssh -N -R …` к VPS и
   авто-переподключается при обрыве (цикл + `ServerAliveInterval`).
3. Оператор на VPS открывает раздел **«Локальная модель»**, указывает путь к
   папке моделей **на ПК** (например `D:\models\llama`), жмёт **«Сканировать»**.
4. ПК-агент сканирует папку, отправляет список `.gguf` на VPS → UI показывает
   доступные LLM (например, `Qwen-9B`).
5. Оператор выбирает модель и жмёт **«Запустить»**.
6. VPS проверяет туннель `127.0.0.1:18080`; при необходимости запрашивает у
   ПК-агента докрутку/подтверждение.
7. **На ПК первый раз за SSH-сессию появляется окно** «VPS просит подключить
   локальную LLM. Разрешить?» → оператор жмёт **«Разрешить»** (запоминается
   до конца SSH-сессии).
8. VPS проверяет `/v1/models` по `127.0.0.1:18080` → включает источник
   `local` с label **`Qwen-9B`**; **имя активной модели в UI — `Qwen-9B`**.
9. Чат отвечает **Qwen-9B**.
10. **Остановить** (кнопка на VPS) или **обрыв** → авто-возврат на слабую
    **`Qwen-2B`** (имя активной модели — снова слабая). При восстановлении
    туннеля (ПК переподключился) — авто-возврат на **`Qwen-9B`**.

## 8. Безопасность

- SSH-ключ на VPS ограничен: `no-pty`, `no-agent-forwarding`,
  `no-X11-forwarding`; при возможности — `command="..."` (только действия
  туннеля) и `permitlisten="127.0.0.1:18080"`.
- Reverse-туннель слушает **только loopback** VPS (`127.0.0.1:18080`), наружу
  не публикуется.
- `--api-key` движка ПК и `RTK_LOCAL_API_KEY` совпадают; ключ — в файле
  `600`, вне git.
- Подтверждение на ПК — обязательное; «отклонить» = туннель не поднимается.
- ufw на VPS: дополнительных внешних портов **не** открываем (туннель идёт
  внутри SSH, порт 22/8443 уже открыты).
- **Windows-ПК:**
  - приватный ключ хранится в `%USERPROFILE%\.ssh\` (ACL — только владелец);
  - используется встроенный **`ssh.exe`** (OpenSSH for Windows, штатный с
    Windows 10/11) либо клиент из Git for Windows;
  - окно-агент не слушает внешних портов (только исходящее соединение к
    VPS и локальные stdin/stdout туннеля);
  - вся коммуникация «VPS↔агент» идёт **внутри** SSH-канала (loopback), не
    через дополнительный открытый порт.

## 9. Тестирование и приёмка

1. **Скан с ПК:** указан путь на ПК (Windows) → список `.gguf` появляется в
   UI VPS.
2. **Подтверждение (окно-агент):** «Запустить» → на ПК появляется окно;
   без «Разрешить» сильная модель не активна, работает `Qwen-2B`.
3. **Подтверждение на SSH-сессию:** после «Разрешить» повторные запросы в
   той же SSH-сессии **не** спрашивают снова; при разрыве и переподключении
   SSH — окно появляется **заново**.
4. **Переключение:** после «Разрешить» **имя активной модели** в UI —
   **Qwen-9B**, чат отвечает сильной моделью.
5. **Остановка:** «Остановить» → снова активна **Qwen-2B**, имя сменилось.
6. **Обрыв и авто-возврат:** убить туннель/выключить ПК → VPS не падает,
   переходит на **Qwen-2B**, статус «ПК недоступен»; после восстановления
   туннеля — **авто**-возврат на **Qwen-9B** без нажатия кнопки.
7. **Безопасность:** порт `18080` и движок ПК недоступны извне; SSH-ключ
   ограничен; логи без тел; приватный ключ Windows — с ACL только владельца.
8. **Автозапуск/переподключение:** агент стартует из автозагрузки Windows и
   сам восстанавливает туннель после сетевого обрыва.
9. **Повторный запуск** идемпотентен (один туннель).

## 10. Принятые решения

| № | Вопрос | Решение |
|---|---|---|
| 1 | Направление туннеля | **ПК держит постоянный reverse-туннель** (вариант B). ПК за NAT, соединение исходящее ПК→VPS |
| 2 | ОС ПК | **Windows** (OpenSSH `ssh.exe`, автозагрузка/Планировщик задач) |
| 3 | Форма подтверждения | **Окно-агент** на ПК («Разрешить / Отклонить») |
| 4 | Частота подтверждения | **Один раз на SSH-сессию** (пока живо SSH-соединение); при переподключении — заново |
| 5 | Обрыв туннеля | **Авто-возврат на `Qwen-2B`**; сильная — только после повторного подключения |
| 6 | Имя модели в UI | Показывается **имя АКТИВНОЙ модели** (слабая или сильная), без списка обеих |

### 10.1. Закрытые вопросы (из раннего списка)

- Порт туннеля на VPS: **`127.0.0.1:18080`** (loopback).
- Триггер туннеля: ПК держит постоянный туннель; **кнопка «Запустить»**
  включает сильную модель; на ПК туннель поднимается агентом при запуске.

### 10.2. Windows-агент и SSH-сессия (детали реализации)

- **Команда туннеля** (на ПК, встроенный OpenSSH):
  ```
  ssh -N -R 127.0.0.1:18080:127.0.0.1:8080 ^
      -o ServerAliveInterval=30 -o ServerAliveCountMax=3 ^
      -o ExitOnForwardFailure=yes rtk@<VPS>
  ```
  `-N` — без команды; `-R` — reverse-форвардинг; `ServerAliveInterval` —
  «keepalive», чтобы VPS замечал обрыв; `ExitOnForwardFailure` — падать, если
  порт на VPS занят.
- **Авто-перезапуск:** окно-агент держит цикл: оборвалось → перезапуск через
  паузу (2–5 с), с экспоненциальной задержкой при частых падениях.
- **«SSH-сессия»** для подтверждения = одно живое SSH-соединение агента.
  Агент хранит в памяти флаг `confirmed` на время сессии; при пересоздании
  соединения флаг сбрасывается → окно спрашивает снова.
- **Связь VPS↔агент:** внутри SSH-канала. Вариант — пробросить на VPS второй
  локальный порт «служебного» API агента (например,
  `-R 127.0.0.1:18081:127.0.0.1:18081`), через который VPS запрашивает скан
  папки и статус подтверждения. Порт **только loopback** VPS.
- **Автозапуск:** ярлык агента в «Автозагрузка» (`shell:startup`) или задача
  в Планировщике («При входе пользователя»). Запуск от обычного пользователя
  (не служба), т.к. нужен доступ к папке с моделями и, возможно, диалог.
- **Модели на ПК:** движок `llama-server.exe` слушает `127.0.0.1:8080`
  (loopback ПК); VPS видит его через туннель как `127.0.0.1:18080`.

## 11. Риски

- **Обрыв туннеля** при смене сети на ПК — митигация: `ServerAliveInterval`,
  авто-перезапуск в агенте, авто-возврат на слабую `Qwen-2B`.
- **Windows-специфика** — зависимость от встроенного OpenSSH (`ssh.exe`);
  при его отсутствии — Git for Windows. Пути — в формате Windows
  (`D:\models\...`), пробелы/кириллица в путях — экранировать.
- **Пропускная способность канала ПК→VPS** может стать узким местом при
  стриминге больших ответов (LLM на ПК мощная, но канал — домашний).
- **Безопасность ключа туннеля** — компрометация даёт доступ к loopback VPS;
  ограничить ключ (`command`, `permitlisten`), ACL на приватный ключ Windows.
- **Конфликт порта `18080`** на VPS, если туннель уже поднят (вторая копия
  агента) — `ExitOnForwardFailure=yes` + идемпотентность агента.
- **Служебный порт агента (`18081`)** — только loopback VPS; не публиковать.
